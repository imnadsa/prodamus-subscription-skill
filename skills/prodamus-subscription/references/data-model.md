# Модель данных подписки

## Где живут поля подписки

Подписка живёт на той сущности, которая **платит**. Обычно это организация
(`clients` / `tenants` / `accounts`), а не пользователь: у одной организации может
быть пять сотрудников с логинами, но платит она одна.

```sql
clients
  slug                     text primary key   -- он же order_num в ссылке оплаты
  subscription_status      text not null default 'expired'
  subscription_expires_at  timestamptz
  gateway_subscription_id  text               -- id подписки в шлюзе (рекуррент)
  billing_email            text
  billing_phone            text               -- нормализованный, только цифры
  known_emails             text[]             -- старые адреса: люди меняют почту
```

`known_emails` — не украшение. Клиент оформил подписку с рабочей почты, через год
сменил её на личную в профиле — и рекуррентное списание перестало находить клиента
по email. Старый адрес должен остаться в поиске.

## Статусы и что они значат

| Статус | Кто ставит | Доступ | Комментарий |
|--------|-----------|--------|-------------|
| `free` | админ вручную | всегда | подарок, бартер, внутренние аккаунты. Дата не проверяется |
| `trial` | регистрация | по дате | пробный период |
| `active` | вебхук при успешной оплате | `now < expires_at` | нормальное состояние платящего |
| `past_due` | вебхук при неудачном списании | `now < expires_at` | шлюз повторяет попытки. **Отсрочки нет** |
| `expired` | вебхук / крон | нет | |

**Про `past_due` отдельно.** Соблазн дать «пару дней на подумать» велик, и мы ему
поддались: сначала `past_due` возвращал доступ безусловно, без проверки даты.
Клиенты, по которым шлюз так и не прислал финальное уведомление, пользовались
сервисом месяцами бесплатно. Потом отсрочку ограничили тремя днями, потом сняли
совсем. Правильно так: **`past_due` = `active` по правам доступа, доступ живёт ровно
до конца оплаченного периода.** Не оплачен день — значит не оплачен.

## Журнал событий

```sql
payment_events
  id           uuid primary key
  client_slug  text            -- null, если клиента не нашли: строка всё равно пишется
  event_type   text            -- payment_success_first | payment_fail_<code> | ...
  amount       numeric
  event_key    text            -- ЗАМОК ИДЕМПОТЕНТНОСТИ, unique where not null
  raw_payload  jsonb           -- сырое тело вебхука целиком
  created_at   timestamptz default now()

create unique index payment_events_event_key_uniq
  on payment_events (event_key) where event_key is not null;
```

Индекс **частичный**: служебные строки (`invalid_signature`, `client_not_found`,
`duplicate_skipped`) пишутся с `event_key = NULL` и под уникальность не попадают —
их может быть сколько угодно.

`raw_payload` хранить обязательно. Когда через полгода клиент скажет «я платил в
марте», единственный способ доказать или опровергнуть — это сырое тело от шлюза.

## Машина переходов

Шлюз шлёт события трёх видов: `action` (действие по подписке), `notification`
(уведомление) и простой статус платежа. Сводим их к одной таблице:

| Событие от шлюза | Новый статус | `expires_at` |
|------------------|--------------|--------------|
| первый платёж / автосписание успешно | `active` | `max(старый, now + период)` |
| списание не прошло, попытки продолжаются | `active` → `past_due`, иначе без изменений | не трогаем |
| списание не прошло, попытка последняя | **не трогаем, пока оплачено**; иначе `expired` | не трогаем |
| клиент отменил автопродление | **не трогаем, пока оплачено**; иначе `expired` | не трогаем |
| подписка деактивирована | **не трогаем, пока оплачено**; иначе `expired` | не трогаем |
| подписка активирована вручную в кабинете шлюза | `active` | `max(старый, now + период)` |
| неизвестное событие | не трогаем | не трогаем |

Два правила, которые превращают эту таблицу в рабочую:

**Правило «оплаченное не отбираем».** Любое закрывающее событие проверяет
`expires_at > now`. Если период ещё идёт — статус остаётся как есть, а доступ
закроется сам, когда дата пройдёт. Иначе клиент, отменивший автопродление на
следующий день после оплаты, теряет весь оплаченный месяц. У нас так потеряли
месяц четверо, пока правило не появилось.

**Правило `max`.** Активирующее событие ставит `expires_at = max(текущий, now + 31)`.
Без этого клиент, которому админ выдал полгода вперёд, после любого платежа
получал ровно месяц — остальное срезалось.

## Второй контур: организация + её единицы

Если платить нужно не только за организацию, но и за каждый её филиал / проект /
рабочее пространство сверх первого — заводится второй контур на дочерней таблице:

```sql
branches
  subscription_status      text not null default 'expired'
    check (subscription_status in ('included','free','active','expired'))
  subscription_expires_at  timestamptz
  gateway_subscription_id  text
  billing_note             text   -- «оплата по счёту», «подарок» — чтобы через
                                  -- полгода помнить, почему тут free
```

- `included` — первый (главный) филиал: покрыт подпиской организации, отдельно не
  оплачивается и **никогда не блокируется**;
- `free` — открыт вручную (оплата по счёту, подарок);
- `active` / `expired` — как у организации.

Порядок гейтов важен: **сначала** проверяется подписка организации (не оплачена —
закрыт весь кабинет), **потом** конкретный филиал (закрыт только он, на оплаченные
можно переключиться).

Три вещи, на которых спотыкаются в этом контуре:

1. **Дефолт колонки — `expired`.** Значит, код создания главного филиала обязан
   явно проставить `included`. Забыли — и клиент упирается в платный экран на
   своём единственном филиале. Поэтому проверку доступа пишем не только по статусу,
   но и по признаку «главный»: `if (branch.is_default) return true`.
2. **Grandfathering.** Вводите платность для дочерних единиц позже старта — все
   существующие на момент миграции получают `free` навсегда. Платными становятся
   только созданные после. Иначе завтра утром часть работающих клиентов увидит
   пейволл — и это будет ваш худший день.
3. **Идентификатор в ссылке.** У платежа за филиал `order_num = branch_slug`, у
   платежа за организацию — `order_num = client_slug`. Различать платежи по сумме
   нельзя: цены меняются, а история остаётся.

## Несколько платёжных кабинетов

Когда продаж становится больше, чем берёт одно ИП, появляется второй кабинет.
Ломать вебхук не нужно: он принимает оба и **перебирает секретные ключи по
очереди** — чей ключ сошёлся с подписью, от того кабинета и платёж. Кабинет
клиента (`clients.gateway_account`) нужен только для того, чтобы построить
правильную ссылку оплаты.

Один нюанс, который стоил нам разбирательства: если у клиента есть старая подписка
в первом кабинете и новая во втором, финальный провал списания по СТАРОЙ прилетит
уже после успешной оплаты по НОВОЙ. Спасает правило «оплаченное не отбираем» —
без него клиент платит и в тот же день упирается в пейволл.
