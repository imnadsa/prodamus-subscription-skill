# Вебхук приёма платежей

Вебхук — единственное место в системе, где меняется статус подписки. Ни админка,
ни фронт, ни крон статус не двигают (админка — только через явное действие
человека, с записью в тот же журнал). Одна точка входа = одно место, где может
сломаться, и одно место, где чинить.

Референс-реализация целиком: [`../assets/webhook.ts`](../assets/webhook.ts).

## 1. Тело запроса

Шлюз шлёт `application/x-www-form-urlencoded` с ключами в PHP-нотации:

```
order_num=tenant-42&sum=1490&subscription[id]=111111&subscription[profile_id]=222222&products[0][name]=Подписка
```

Нужен парсер, который соберёт из этого объект: `subscription[id]` → вложенный
объект, `products[0][name]` → массив объектов. И одна тонкость: если пришли
`products[0]` и `products[2]` без `products[1]`, получится разреженный массив,
а `JSON.stringify` превратит дырку в `null` — подпись не сойдётся. Массивы надо
уплотнять (`.filter(Boolean)`).

## 2. Подпись — HMAC-SHA256 по каноническому JSON

Алгоритм Продамуса (в других шлюзах отличается, суть та же):

```
1. рекурсивно отсортировать ключи по алфавиту, включая вложенные объекты
2. привести ВСЕ скаляры к строкам: 1490 → "1490", true → "true", null → ""
3. JSON.stringify без пробелов, кириллица как есть (не \uXXXX)
4. заменить "/" на "\/"          ← вот это забывают все
5. hmac_sha256(payload, secret_key) в hex
6. сравнить с заголовком Sign
```

Четвёртый пункт — причина почти всех «подпись не сходится». PHP `json_encode`
экранирует слеши по умолчанию, `JSON.stringify` в JS — нет. Любой URL внутри
payload (а он там есть) ломает подпись.

Второй по частоте — trailing `\r\n` в значениях: в form-urlencoded теле текстовое
поле может приехать с переводом строки, которого не было при подписи. Срезайте
хвостовые `\r\n` (только хвостовые — обычные пробелы могут быть значимыми).

Не сошлось — **пишем событие `invalid_signature` в журнал вместе с сырым телом и
посчитанной подписью** и возвращаем 401. Диагностика потом делается по журналу,
а не по логам контейнера, которые через сутки ротируются.

## 3. Что именно оплатили

Определяется по `plan_id` тарифа. В Продамусе это `subscription.id` — общий для
всех подписчиков этого тарифа. Не путать с `subscription.profile_id` — это id
конкретного подписчика, и у одного клиента он **одинаковый** для всех его подписок.

```ts
const PLAN_MAIN   = ['<id тарифа основной подписки>'];
const PLAN_EXTRA  = ['<id тарифа доп. единицы>'];
const PLAN_OTHER  = ['<id чужих продуктов того же кабинета>'];
```

Зачем это нужно: если на кабинете продаётся ещё что-то (второй продукт, клуб,
курс), то без разбора по тарифу **любой** успешный платёж будет продлевать
основную подписку. У нас так раздали лишние недели и месяцы, пока не свели платежи
с тарифами.

Неизвестный тариф лучше засчитать как основную подписку, чем потерять: клиент
заплатил — он должен получить доступ. Но событие в журнале пометьте отдельно.

## 4. Поиск клиента — четыре попытки по очереди

```
1. order_num  → clients.slug            (первый платёж: мы сами положили slug в ссылку)
2. subscription.profile_id → clients.gateway_subscription_id   (рекуррент)
3. email (+ known_emails)               (fallback)
4. телефон, нормализованный             (fallback)
```

Три ловушки:

- **Дубли.** Один email может оказаться у двух организаций. Запрос вида
  «взять единственную строку» вернёт ошибку или null — и клиент «потеряется» на
  каждом рекурренте. Всегда `limit 1`, приоритет активному.
- **Ошибка базы ≠ «не найден».** Многие клиенты БД не бросают исключение, а
  возвращают `{data: null, error}`. Если `error` проигнорирован, сбой базы выглядит
  как «такого клиента нет», вы отвечаете 200, шлюз считает доставку успешной и
  **больше не повторяет**. Платёж потерян. Проверяйте `error` отдельно и отвечайте 500.
- **Клиента правда нет** (оплата с лендинга до регистрации): если `order_num`
  похож на uuid вашей таблицы заказов — создайте клиента прямо здесь, из данных
  платежа, и отправьте приглашение владельцу.

После успешного поиска **дозаполните пустые поля** клиента (id подписки, email,
телефон) — тогда следующий рекуррент найдётся с первой попытки.

## 5. Идемпотентность — на UNIQUE-индексе

Шлюзы ретраят доставку часами и умеют присылать две доставки одновременно.
Проверка «а не было ли такого события в последние 60 секунд» (check-then-act)
не спасает: поздний ретрай проходит мимо окна, две одновременные доставки
проходят обе.

Правильно:

```ts
const eventKey = [slug, orderNum, statusOrAction, amount, payloadDate].join('|');

// 1. пишем событие ДО применения статуса
const { data: ev, error } = await db.from('payment_events')
  .insert({ ...event, event_key: eventKey }).select('id').single();

if (error?.code === '23505') {          // нарушение UNIQUE = это повтор
  await logDuplicate();                 // служебная строка без event_key
  return ok({ note: 'duplicate skipped' });
}
if (error) return status500();          // не смогли записать — пусть ретраит

// 2. применяем статус
const { error: updErr } = await db.from('clients').update(payload).eq('slug', slug);
if (updErr) {
  await db.from('payment_events').delete().eq('id', ev.id);  // СНИМАЕМ ЗАМОК
  return status500();
}
```

Про удаление события при неудачном апдейте: если этого не сделать, замок останется
в базе, ретрай шлюза упрётся в `23505`, и статус не применится **никогда**.
Клиент заплатил, событие в журнале есть, доступа нет — и никто не понимает почему.

## 6. Коды ответа

| Ситуация | Ответ | Почему |
|----------|-------|--------|
| всё применилось | 200 | |
| повтор (23505) | 200 | доставка успешна, делать нечего |
| подпись не сошлась | 401 | ретрай не поможет |
| нет заголовка подписи | 400 | |
| сумма ниже минимальной | 400 | |
| ошибка базы (поиск / вставка / апдейт) | **500** | нужен ретрай |
| клиент честно не найден | 200 + событие `client_not_found` | ретрай не поможет, но след остаётся |
| неизвестное исключение | 500 | |

Принцип простой: **200 — это обещание «мы разобрались»**. Даёте 200 там, где на
самом деле не разобрались — платёж исчезает.

## 7. Побочные эффекты

Уведомление в мессенджер, письмо владельцу, пинг смежной системы — только через
`await`. В serverless воркер сносится сразу после возврата ответа: `void fn()` и
даже `waitUntil` в ряде рантаймов молча не выполняются. Мы так потеряли целый
журнал обращений — в нём не оказалось ни строки.

И жёсткий таймаут на каждый внешний вызов (3–5 секунд) плюс `try/catch`: сторонний
сервис не должен уронить обработку платежа. Не дошло уведомление — не страшно,
не применился платёж — страшно.
